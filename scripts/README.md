## Selected execution model

1. An administrator runs `scripts/infra-up.sh` on their workstation while authenticated with Azure CLI. Terragrunt runs locally using that account and the existing state backend.
2. PostgreSQL creation tries `B_Standard_B1ms`, then `B_Standard_B2s`, then `B_Standard_B2ats_v2` only for Azure capacity/SKU-availability errors; each candidate gets a fresh plan, and the existing server SKU is reused on later runs. After the infrastructure stacks are ready, the workstation gathers only non-secret Terraform outputs and current non-secret dev Helm values.
3. The workstation uses Azure VM Run Command to trigger the private operator VM. No SSH/Bastion login is required for automation, and no Azure user credentials are copied to the VM.
4. The VM fetches **public GitHub `main`**, logs into Azure using its system-assigned managed identity, retrieves an admin kubeconfig into `/dev/shm`, and runs Ansible locally. It removes the temporary kubeconfig, Azure CLI cache and generated values file afterward. Only after a success marker is returned does the workstation destroy the four temporary operator-access stacks and deallocate the operator VM; a future `infra-up` reapplies the grants and starts the VM. Azure Bastion Developer remains provisioned.

`infra-up.sh` checks that relevant local files match published `origin/main` and stops before planning/applying if they do not. The playbooks will not be available to a VM until the reviewed changes are merged/published to `main` by the repository owner. This assistant will not push them.

Azure Run Command requires a healthy VM agent and outbound access from it to Azure public endpoints and GitHub/Helm/Gateway release endpoints. The workstation identity must be allowed to invoke VM Run Command, create/delete the temporary role assignments, and start/deallocate the VM. Azure Bastion Developer is a separate free service; the billable compute resource is the operator VM. After successful Ansible and temporary-role cleanup, the VM is deallocated; on a later `infra-up`, it is started before Run Command. Its OS disk and other attached resources remain. Run Command output is limited; secret-bearing Ansible tasks use `no_log`, and secret values are never included in the Run Command input.

## Ansible workflows

`ansible/playbooks/site.yml` runs these steps in order on the operator VM:

- `postgresql.yml`: `scripts/provision_postgresql.py` retrieves `postgresql-admin-password` from the operator vault in memory, creates/verifies the `chat_app` role and grants, and creates `database-url` in the app vault only if absent. It fails closed on an unexpected role/secret mismatch. The write is resumable if the role creation fails after the URL is stored.
- `runtime-secrets.yml`: `scripts/provision_runtime_secrets.py` creates Redis URL and Better Auth secret once. If both already exist, reruns leave them untouched; if only one exists, it stops for manual recovery. Redis keys are read from ARM in memory.
- `kubernetes.yml`: installs Gateway API v1.4.1 CRDs and NGINX Gateway Fabric 2.9.1, creates namespace `chat`, applies TLS via `scripts/provision_tls_secret.py`, runs the migration Helm release, then deploys the app release and waits for rollout.
- `preflight.yml`: checks required non-secret inputs and temporary access files are present.

The app's runtime passwords/keys are never copied into the operator vault, command arguments, values file, or repo. PostgreSQL and TLS helper failures emit generic messages; inspect Azure role/network metadata and Ansible task output, not secret values.

`render_dev_values.py` copies the pinned image digests from `deploy/environments/dev/chat-values.yaml` and replaces recreated non-secret identity, vault, endpoint and IP names with Terraform outputs. It writes only to stdout; the workstation passes the resulting YAML to the VM through Run Command. It refuses unpinned image references. It does not build/publish images or verify the referenced digests exist in ACR; image publishing/verification remains a prerequisite.

## Wrapper safety

An Azure PostgreSQL SKU is the server's compute/performance tier and affects cost; it is not a password or database name. New server creation tries `B_Standard_B1ms` → `B_Standard_B2s` → `B_Standard_B2ats_v2` on capacity/SKU-availability failures, replanning each time. Existing servers keep their current SKU to avoid accidental resizing. Confirm current policy, regional availability, quota and pricing before applying; B2ats_v2 has 2 vCores but 1 GiB memory, so verify it suits the dev workload.

- `infra-up.sh` checks the active subscription is the known dev subscription and fails closed if the app vault is still soft-deleted. For a new PostgreSQL server it tries the configured SKU sequence on capacity/SKU-availability errors; for an existing server it uses the server's actual SKU. The wrapper prompts to use `~/.ssh/chat-operator.pub` by default; answering no selects another public-key file. A missing/unreadable default or selected key aborts. The helper reads the key file and sets `OPERATOR_SSH_PUBLIC_KEY` for Terragrunt.
- At the PostgreSQL stack, `terragrunt_with_postgres_admin_secret.py` checks whether the server exists. If absent, it reuses an already-staged secret across retries, creating a new random secret version only if none exists; for an existing server it reads the current secret. It temporarily allows the workstation IP only when needed, asks `[Y/n]` confirmations (Enter/Y accepts), and removes any rule it added before invoking Terragrunt. The password is only placed in the child process environment; it is not printed or put in argv/state. The wrapper replans each candidate SKU and retries only capacity/SKU-availability errors. For changing stacks, it saves the exact plan owner-only. Without `-y`, each apply and each post-success temporary-role destroy plan gets its own review and `[Y/n]` prompt; with `-y`, mutating commands receive `-auto-approve`. After confirmed Ansible success, it removes temporary access stacks and deallocates the operator VM; on failed/unconfirmed Ansible it leaves them for troubleshooting.
- `infra-down.sh` retrieves the current password through the same temporary `[Y/n]` access-confirmation path only for the PostgreSQL destroy plan/apply; it never rotates the secret. It then follows the teardown approvals and app-vault-only purge guard. After up completes, Ansible on the operator VM independently reads the admin secret through its managed identity. Neither wrapper sends secret values to the VM.
- `infra-down.sh` checks the subscription and plans the saved PostgreSQL state for teardown without rotating its admin secret; it loads the operator SSH public key using the same prompt, then asks the operator to remove/verify the Cloudflare DNS record and reviews each dev-only destroy plan. Without `-y`, it requires a stack-specific typed approval before each destroy; with `-y`, it adds `-auto-approve` to each listed dev destroy. DNS and app-vault purge confirmations remain required. For the PostgreSQL stack it reads the current admin secret through the temporary access path, without rotating it. After the app Key Vault stack is destroyed, it separately requires the exact `purge chat-dev-cf816eae-kv` confirmation before purging that soft-deleted vault. It does not target shared stacks, the resource-group stack, retained ACS/Email, Web PubSub, ACR, Cosmos account, operator vault or state backend. It destroys workload federation before AKS so Terragrunt can still resolve the AKS dependency.

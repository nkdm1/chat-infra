## Start or rebuild

1. Check the remaining credit and actual bill, target subscription, approved SKUs, name availability, and remote-state recovery/locking. Include charges for retained resources and the safety margin. Set `ARM_SUBSCRIPTION_ID` and review the dev stack's pinned `B_Standard_B1ms` PostgreSQL SKU for current policy, availability and cost. Verify the chosen dev Redis `Balanced_B0` and non-HA setting against the cost and availability review. These are not recommendations or evidence of regional availability.
2. Review individual shared and dev resource groups, dev network, shared registry, shared Cosmos account and dev workload identity. Preserve the shared account and registry independently of dev. Review the state key and dependencies before approving any action. The network stack owns both static public IPs, which continue to be billed without AKS.
3. Review the private data services and their dev endpoints/DNS: Cosmos database and private endpoint, the Denmark PostgreSQL network and its peerings before PostgreSQL, Blob Storage and endpoint, Key Vault and endpoint, and Redis and endpoint. PostgreSQL private DNS must link both the Denmark and Belgium VNets; inter-region peering adds data-transfer charges. Also review Free-tier Web PubSub's public endpoint, accepted lack of network ACLs, and ACS with its Azure-managed domain. Verify public access settings and application identity roles. Cost each persistent service and endpoint. Never expose account keys or private credentials in CLI output or logs.
4. From an approved private operator path, create a least-privilege PostgreSQL application login and database URL with TLS; provision `database-url`, `redis-url`, and `better-auth-secret` in the dev Key Vault. See `docs/postgresql-provisioning.md` for the completed dev SQL steps and `docs/runtime-secret-provisioning.md` for the secret setup and future automation requirements. The optional `operator-access` stack configures a temporary Denmark East VM and Bastion Developer. The VM has no public IP; its NSG permits SSH from the `VirtualNetwork` service tag (including peered networks) and denies other inbound traffic. Default outbound access is enabled for package installation. Browser SSH, PostgreSQL TLS login, Key Vault private DNS/TCP and a temporary AKS CSI secret-mount probe have succeeded; app connections and end-to-end behavior remain untested. The VM's system identity initially has no Key Vault or Redis roles. A separate temporary `operator-aks-access` stack links the AKS system private DNS zone to the operator VNet and grants the VM `Azure Kubernetes Service Cluster Admin Role` on the cluster; this grants full Kubernetes administrative access and was selected for private TLS-secret provisioning. Revoking the Azure role does not invalidate issued local admin client certificates; treat kubeconfig as a secret, avoid persisting it to disk, and review credential rotation and residual exposure. The user selected a separate temporary `operator-secret-access` stack granting the built-in Key Vault Secrets Officer role, scoped to the dev vault; this includes read, overwrite, delete and purge of its secrets. Review its plan and remove the role after use. A separate temporary `operator-redis-access` stack grants only the Redis database `listKeys` operation, which exposes both access keys to the VM identity and VM administrators. Review its plan, use it only for secret provisioning, and remove it afterward. The PostgreSQL administrator password is separate: never place it in the app-readable vault, command arguments, shell history, Terraform state, or chat. Confirm how Azure Managed Redis keys and ACS provider keys are protected in remote state.
5. Review the AKS stack only after the network and registry are ready. Review the `workload-federation` stack after AKS exists: its issuer changes when a cluster is recreated. Ensure the operator has the least-privilege Run Command access and the private endpoint/DNS paths work from pods.
6. Review and manually publish the app and migrator images via the configured GitHub OIDC workflow. Select immutable digests. Install the reviewed Gateway API CRDs and NGINX Gateway Fabric; provision the Cloudflare Origin CA certificate and proxy/Full (strict) configuration safely. Follow `deploy/README.md` to run the one-off migration before application rollout. Do not put secrets or certificate keys in Git, shell history, chart values or logs.
7. Smoke-test HTTPS origin, `/api/health`, `/api/ready`, identity and private access, authentication and revocation, email verification, chat persistence, live events and polling fallback, attachments, admin functions and Redis fallback. Confirm that Redis and Web PubSub degradation alone do not fail readiness. Record the results and actual cost.

## Stop or destroy — only after explicit approval

1. Agree whether dev application data and secrets are to be retained; understand that destruction of database, storage, Key Vault, Redis or resource-group stacks can lose data. Back up or preserve what was selected, and verify retention/recovery before any destructive operation. Do not delete shared or prod resources.
2. Remove the dev workload federation before destroying/recreating AKS, then review the AKS stack's destroy plan independently. Recreate federation against the new issuer on the next start. Confirm Azure actually removes the AKS cluster and cluster-owned resources. The app, migration Jobs, Kubernetes secrets and Origin CA secret on that cluster must be recreated; preserve certificate material only through approved secure procedures.
3. Decide separately whether to stop or destroy each dev PaaS resource and endpoint. PostgreSQL stop has service-specific restart limits and may continue storage/backup charges; verify current Azure behavior and actual billing. Redis and other independent PaaS services must not be assumed stopped when AKS is deleted. A retained private endpoint, DNS zone, public IP, ACR, Cosmos account and state storage can continue billing.
4. Review targeted destroy plans for `operator-aks-access`, `operator-redis-access` and `operator-secret-access` first, then the temporary `operator-access` stack, as soon as their task is complete. Remove the temporary AKS DNS link before deleting the cluster/system-managed zone. Deleting the cluster-admin Azure role does not revoke an already-issued admin client certificate; review credential rotation and kubeconfig/VM disk cleanup explicitly. The VM and disk are billable; deallocation does not remove disk charges. Remove any other separately granted temporary roles. If PostgreSQL is to be destroyed, review it before the Denmark East PostgreSQL network, which depends on the Belgium app network; preserve or destroy each only with explicit approval. Verify the live resource inventory, state and current bill after shutdown. Record retained resources, whether public DNS now points at an unavailable gateway, remaining credit, and actions needed for the next session. Never assume a successful cluster deletion means spending has stopped.

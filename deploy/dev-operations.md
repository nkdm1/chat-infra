# Dev session operations — draft, untested

This is an operator checklist, not an authorization to provision or destroy. Complete the subscription, backend, region/SKU, quota, lifecycle-cost and $100 credit preflight in `docs/TODO.md` before any plan or apply. Review each stack independently; never run a broad `run-all destroy`. Private data access, operator identity, DNS, credential provisioning, Gateway, TLS, GitHub OIDC and all lifecycle steps remain to be tested.

## Start or rebuild

1. Check the remaining credit and actual bill, target subscription, approved SKUs, name availability, and remote-state recovery/locking. Include charges for retained resources and the safety margin. Set `ARM_SUBSCRIPTION_ID`, and select reviewed `POSTGRESQL_SKU`, `REDIS_SKU`, and `REDIS_HIGH_AVAILABILITY` where relevant. These are not recommendations or evidence of regional availability.
2. Review individual shared and dev resource groups, dev network, shared registry, shared Cosmos account and dev workload identity. Preserve the shared account and registry independently of dev. Review the state key and dependencies before approving any action. The network stack owns the NAT Gateway and both static public IPs, and continues to be billed without AKS.
3. Review the private data services and their dev endpoints/DNS: Cosmos database and private endpoint, PostgreSQL, Blob Storage and endpoint, Key Vault and endpoint, and Redis and endpoint. Also review Free-tier Web PubSub's public endpoint/ACL and ACS with its Azure-managed domain. Verify public access settings and application identity roles. Cost each persistent service and endpoint. Never expose account keys or private credentials in CLI output or logs.
4. From an approved private operator path, create a least-privilege PostgreSQL application login and database URL with TLS; provision `database-url`, `redis-url`, and `better-auth-secret` in the dev Key Vault. The PostgreSQL server administrator password is a separate ephemeral/write-only input supplied securely to OpenTofu via `TF_VAR_administrator_password` when required. Its version input must be incremented when rotating. Do not use the administrator as the app login. Confirm how Azure Managed Redis keys and ACS provider keys are protected in remote state.
5. Review the AKS stack only after the network and registry are ready. Review the `workload-federation` stack after AKS exists: its issuer changes when a cluster is recreated. Ensure the operator has the least-privilege Run Command access and the private endpoint/DNS paths work from pods.
6. Review and manually publish the app and migrator images via the configured GitHub OIDC workflow. Select immutable digests. Install the reviewed Gateway API CRDs and NGINX Gateway Fabric; provision the Cloudflare Origin CA certificate and proxy/Full (strict) configuration safely. Follow `deploy/README.md` to run the one-off migration before application rollout. Do not put secrets or certificate keys in Git, shell history, chart values or logs.
7. Smoke-test HTTPS origin, `/api/health`, `/api/ready`, identity and private access, authentication and revocation, email verification, chat persistence, live events and polling fallback, attachments, admin functions and Redis fallback. Confirm that Redis and Web PubSub degradation alone do not fail readiness. Record the results and actual cost.

## Stop or destroy — only after explicit approval

1. Agree whether dev application data and secrets are to be retained; understand that destruction of database, storage, Key Vault, Redis or resource-group stacks can lose data. Back up or preserve what was selected, and verify retention/recovery before any destructive operation. Do not delete shared or prod resources.
2. Remove the dev workload federation before destroying/recreating AKS, then review the AKS stack's destroy plan independently. Recreate federation against the new issuer on the next start. Confirm Azure actually removes the AKS cluster and cluster-owned resources. The app, migration Jobs, Kubernetes secrets and Origin CA secret on that cluster must be recreated; preserve certificate material only through approved secure procedures.
3. Decide separately whether to stop or destroy each dev PaaS resource and endpoint. PostgreSQL stop has service-specific restart limits and may continue storage/backup charges; verify current Azure behavior and actual billing. Redis and other independent PaaS services must not be assumed stopped when AKS is deleted. A retained private endpoint, DNS zone, public IP, NAT Gateway, ACR, Cosmos account and state storage can continue billing.
4. Verify the live resource inventory, state and current bill after shutdown. Record retained resources, whether public DNS now points at an unavailable gateway, remaining credit, and actions needed for the next session. Never assume a successful cluster deletion means spending has stopped.
